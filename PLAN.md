# Plan.md: Реализация и проверка micro-MVP «Кто выгуливает Бориса»

## 1. Текущий статус

- Приоритет: подготовить итоговые материалы по принятому приложению без дальнейшей полировки и расширения функциональности.
- Текущее состояние: шаги 1–5 реализованы, проверены агентом через HTTP, SQLite, Chrome и Edge и приняты студентом после ручных проверок; состояние сохранилось после полного перезапуска сервера. Шаг 6 не начат.
- Основная цель цикла: создать семь скриншотов, карточку кейса и демо на основании принятой рабочей версии.
- Обязательные ограничения: одна общая страница, пять фиксированных слотов только на текущую дату, только синтетические данные, SQLite как единственное хранилище, атомарная серверная защита от повторной записи; без авторизации, отмены записей, дополнительных сценариев, внешних интеграций и обязательного деплоя.
- Основной контекст проекта: неизменяемые `spec.md` и `AGENTS.md`, фактическое описание и запуск в `README.md`, статусы и проверки в этом `PLAN.md`.
- Текущий активный шаг: 6.

## 1.1 Целевой сценарий

1. Сотрудник открывает общую страницу на широком или узком экране.
2. Видит текущую дату, пять фиксированных слотов и состояние каждого слота.
3. Выбирает свободный слот, вводит непустое синтетическое ФИО и подтверждает запись.
4. Видит занятый слот с введённым ФИО; занятый слот не предлагает повторную запись.
5. При повторной попытке занять тот же слот получает понятный серверный отказ, а первоначальная запись остаётся неизменной.
6. После обновления страницы и открытия во втором браузере видит сохранённое состояние.
7. Отдельно отмечает кормление синтетическим ФИО и видит обновлённые время и ФИО в карточке последнего кормления.

## 2. Требования к результату

- `spec.md`: остаётся неизменным единственным источником продуктовых требований; результат должен пройти все семь DoD и контролируемый smoke-check.
- `README.md`: кратко описывает назначение, пользователя, главный сценарий, ожидаемый результат и состав пакета; после реализации дополняется фактическими запуском, сценарием и границами без дублирования плана.
- `AGENTS.md`: остаётся неизменным; его постоянные правила ограничивают реализацию и порядок приёмки.
- `PLAN.md`: содержит отдельный результат и проверку каждого шага; активный шаг, статусы и фактические проверки обновляются после принятия изменений студентом.
- Границы текущего этапа: реализуются только функции из `spec.md`; полировка прекращается после выполнения семи DoD; скриншоты, карточка кейса и демо создаются только после завершения проверок пользователем.

## 3. Что делаем по шагам

- [x] 1. Подготовить минимальный Node.js-проект и SQLite
  - Действие: создать локальный запуск через npm, подключить совместимый SQLite-драйвер, реализовать схему и создание пяти свободных слотов текущей даты при их отсутствии.
  - Результат: приложение запускается локально, а в SQLite-файле существуют заданные таблицы и пять фиксированных записей на текущую дату.
  - Проверка: выполнить запуск через npm и убедиться, что сервер стартует, файл SQLite создан, время слотов соответствует `spec.md`, повторный запуск не дублирует записи.
  - Фактическая проверка агентом: `npm start` успешно запускает сервер на Node.js 24.21.0; встроенный `node:sqlite` создаёт обе таблицы; после перезапуска остаются ровно пять записей без дубликатов.

- [x] 2. Реализовать серверную запись на прогулку
  - Действие: добавить получение слотов и запись по непустому после очистки пробелов ФИО через одну атомарную операцию обновления или транзакцию с обработкой конфликта.
  - Результат: свободный слот сохраняет ФИО и время записи, а повторный запрос возвращает понятный конфликт и не меняет первоначальную запись.
  - Проверка: отправить реальные запросы на запись свободного и затем того же занятого слота, проверить ответы и неизменность данных в SQLite, включая попытку записи с пустым ФИО.
  - Фактическая проверка агентом: запись `09:00` получила HTTP 201 и сохранила «Анна Тестова» после очистки пробелов; пустое ФИО получило HTTP 400; повторная запись получила HTTP 409, а исходные ФИО и время в SQLite не изменились.

- [x] 3. Собрать общую страницу записи на прогулку
  - Действие: показать текущую дату и пять слотов, различить свободные и занятые состояния, добавить ввод ФИО, подтверждение и вывод серверного отказа.
  - Результат: сотрудник проходит главный сценарий в браузере, видит ФИО в занятом слоте и не получает доступное действие повторной записи.
  - Проверка: в браузере занять свободный слот, проверить отображение состояния и отказ при повторной попытке, затем обновить страницу и открыть приложение во втором браузере.
  - Фактическая проверка агентом: в Chrome выполнена запись на `11:00` и `13:00`, состояние сохранилось после обновления и отобразилось в Edge; повторная отправка из устаревшей формы Edge получила понятный отказ, первоначальное ФИО осталось без изменений.
